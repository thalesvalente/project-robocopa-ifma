## Contexto, hipóteses e Constituição

O núcleo PG-01..06 comprova transações SQL, mas ainda recebe um descriptor que pressupõe admissão prévia. O I1 valida RoboDSL, porém ainda não foi ligado ao PostgreSQL por driver real. Este incremento realiza essa ligação, sem inventar autenticação de usuário/worker. A documentação vigente D-009 mantém Vercel Hobby preferencial no contexto voluntário informado, Supabase como destino canônico e VM dedicada apenas para computação. Os experimentos SQLite/mTLS anteriores continuam preservados.

## Decisões técnicas e pesquisa

1. Reusar `services.worker_agent.contracts.admit` e o compilador RoboDSL existente, sem portar a linguagem nem habilitar código geral. O serviço recebe contexto de ator SOMENTE de um chamador interno confiável, separado do JSON. Isso não verifica JWT; a API futura deverá autenticar e autorizar o ator antes de chamar o serviço.
2. Migration **002**, sem reescrever 001: projeção privada de versões previamente aprovadas, com owner/escopo/version_id, hashes de fonte/programa/Java, estado ativo e revisão. Não guardar fonte, chave ou PII no schema de controle. Registrar versões pertence à futura API de autoria; neste recorte apenas a fixture administrativa registra versões conhecidas.
3. Novo papel NOLOGIN `rc_admission`: somente funções de consulta de versão autorizada e enfileiramento admitido, sem tabelas, gate, claim, heartbeat ou privilégios de worker. Revogar do papel `rc_broker` a entrada direta `enqueue` após migration 002; só o owner interno poderá utilizá-la através da função de admissão. O broker de execução conserva as operações já testadas, não recebe um bypass da admissão.
4. A consulta inicial é curta; compilação fora da transação. Antes de inserir, uma segunda transação confere novamente owner/escopo/versão, revisão ativa e hashes, sob lock consistente com settings. Revogação ou mudança de política entre consulta e gravação deve negar; nunca confiar somente no snapshot Python. Hashes da versão não podem ser alterados em lugar: nova versão é novo registro.
5. JSON de entrada restrito a schema_version, version_id, idempotency_key e rounds. IDs de job/tentativa, owner, worker, política, hashes e deadline não são escolhidos pelo cliente. IDs internos descartáveis satisfazem o contrato legado do I1; IDs canônicos e deadline de execução são gerados pelo PostgreSQL. Retry idêntico conserva job e deadline originais, inclusive sem worker disponível. Não duplicar SQLite/pgmq.
6. Adaptador Python com consultas SQL fixas e parâmetros separados, transações curtas, commit confirmado antes de sucesso, erros sanitizados e `prepare_threshold=None`. Usar Psycopg 3 fixado em versão/hash; nenhuma credencial/connection string padrão ou configuração automática de host. Uma falha de commit gera resultado desconhecido/indisponível; retry com mesma chave pode reconciliar, nunca repetir silenciosamente a inserção.
7. API cloud continua candidata Supabase Edge Functions. Este adaptador Python não roda no Deno por pressuposição: o contrato SQL é compartilhável; autenticação JWT, cliente Deno/HTTP, integração Supabase real e worker outbound serão outra subentrega. Não contar este núcleo como deploy ou autenticação pública.

Fontes primárias consultadas em 2026-10-10: [Psycopg parâmetros](https://www.psycopg.org/psycopg3/docs/basic/params.html), [transações](https://www.psycopg.org/psycopg3/docs/basic/transactions.html), [prepared statements](https://www.psycopg.org/psycopg3/docs/advanced/prepare.html), [Supabase conexões/pooler](https://supabase.com/docs/guides/database/connecting-to-postgres), [funções/privilégios](https://supabase.com/docs/guides/database/functions), [Edge Auth](https://supabase.com/docs/guides/functions/auth), [PostgreSQL SECURITY DEFINER](https://www.postgresql.org/docs/17/sql-createfunction.html). Preferência por SQL parametrizado e owner de privilégio mínimo; modo de pooler/SSL do projeto remoto deverá ser comprovado no deploy, não presumido por teste Unix socket.
